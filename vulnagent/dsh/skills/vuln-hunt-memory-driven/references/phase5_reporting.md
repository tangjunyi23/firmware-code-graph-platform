# Phase 5: Reporting

1. Each vulnerability must be reported to the user.
2. **报告必须包含**：
   - **漏洞根因函数名**（精确到函数级别）
   - 漏洞类型（必须与用户指定类型一致）
   - Source->Sink 完整路径
   - **每一跳的代码片段和解释**（不是仅列函数名，而是贴出关键代码并解释数据流转）
   - 触发条件和利用前提
   - 影响评估
   - **认证管线分析结果**（Pre-auth 类漏洞）
3. Final report saved to `FINAL.md`

### FINAL.md 质量要求（MANDATORY）

1. **代码片段完整性**：每个跳转必须贴出实际代码片段（不是伪代码或自然语言描述），标注文件名和行号
2. **解释充分性**：每段代码后必须有解释，说明数据如何流转、攻击者控制了什么、为什么构成（或不构成）漏洞
3. **认证管线章节**：Pre-auth 类漏洞必须包含认证管线分析结果，引用 `call_graphs.md` 中的管线图
4. **排除候选详细性**：被排除的候选必须给出具体的阻断代码和详细解释，不允许笼统的"不可利用"结论
5. **对比分析**（如适用）：当同类目标存在防护差异时（如一个固件有 `tp_system` 过滤而另一个没有），必须贴出两侧代码进行对比
6. **约束和限制**：必须明确列出利用的实际约束（如 payload 长度限制、字符集限制、需要的前置知识等），不做过度乐观的利用声明
